A Paper plugin that merges multiple Minecraft resource packs into a single pack, uploads it to a configurable hosting provider, and automatically distributes it to players on join. Designed for servers and networks that need to combine packs from different sources into one seamless download.

## Quick start (zero config)

1. **Install the jar.** Put `packmerger-plugin-1.4.1.jar` into `plugins/` and start the
   server once (Paper 26.1+ / Folia, Java 25).
2. **Add packs.** Drop resource packs (zips or unzipped folders) into
   `plugins/PackMerger/packs/`, and datapacks into your world's datapacks folder
   (`world/datapacks/`, i.e. `<level-name>/datapacks/`) as usual. PackMerger finds the
   resource packs that belong to those datapacks on its own (also ones the datapack
   declares on Modrinth) and merges everything into one pack — no restart needed.
3. **Open the port.** The built-in web server hosts the pack on the **Minecraft port + 1,
   TCP** (e.g. `25566` when the server runs on `25565`). Allow that port in the **firewall
   of the server machine** (LAN players need this too, e.g. Windows Defender Firewall) and
   forward it on your router or hosting panel for players on the internet. (On a host
   where you cannot open a port, see [Upload Provider](#upload-provider).) The startup log
   line `Pack URL mode: ...` names the port.
4. **Done.** Every player gets the merged pack when they join, from the same address they
   typed to join (LAN IP, public IP or domain) plus that port, so no host or URL has to be
   configured. The pack is **required**: a player who declines is kicked, and so is a
   player whose download still fails after 3 automatic retries (a broken URL or a pack the
   client cannot load never kicks, and if downloads fail for 3 different players before
   anyone has loaded the pack, PackMerger assumes a closed port, stops kicking for failed
   downloads and logs how to fix it, until a download works again). Turn enforcement off
   with `distribution.enforce-required.enabled: false`.

Behind Velocity/BungeeCord, with proxy-protocol (TCPShield, ...), or when players join
through an SRV record or a tunnel (playit.gg, ...) that does not forward the extra port,
the address players type does not lead to the pack port: set
`upload.self-host.public-url` (or `public-host`) to an address that does.

Players only ever download the **resource pack**. Datapacks stay on the server; only
their `assets/` (textures, models, sounds, lang, …) are copied into the merged pack, never
their `data/`. What datapack discovery cannot do is listed under
[Limitations](#limitations--when-a-datapacks-resource-pack-cannot-be-found); the most
common cases: a resource pack that is only linked in a datapack's description (download
it and put it into `packs/`), datapacks that are not the unmodified Modrinth file (no
Modrinth lookup possible), and datapacks in other worlds' folders (Paper only loads
`<level-name>/datapacks/`, so those are listed but not merged).

Upgrading from an older PackMerger? Your `config.yml` is not changed. If players are not
forced to download the pack there (`required` / `enforce-required` off), PackMerger logs
one line on startup saying which two settings to turn on.

## Features

- **Automatic plugin-pack discovery** — detects packs generated by 19 other plugins (Oraxen, Nexo, ItemsAdder, ModelEngine, EliteMobs, FreeMinecraftModels, Nova, BetterHUD and more), re-merges on its own when one rebuilds its pack, and lets you declare adapters for any other plugin in config — no manual file copying. Unlike file-overwrite mergers, these go through the format-aware merge strategies, so CustomModelData overrides, 1.21.4+ item-definition dispatch entries, lang keys, atlas sources, sounds and fonts from several plugins combine instead of clobbering each other
- **Datapack resource packs** — finds the resource packs that belong to the server's datapacks (assets next to `data/`, a resource pack folder or zip inside the datapack, or a resource pack the datapack declares on Modrinth, downloaded and verified automatically) and merges them like any other pack; a datapack's `data/` never ends up in the resource pack. See [Datapack Resource Packs](#datapack-resource-packs)
- **Other pack hosts detected and fixed** — warns (console, `/pm status`, admin join notice) when ItemsAdder, Oraxen or Nexo also host or send their own pack, or when ItemsAdder protects or compresses its zip so it can't be merged; `/pm fixup <itemsadder|oraxen|nexo>` backs up that plugin's config and writes the change, `/pm fixup dismiss` hides the warning
- **Priority-based merging** — control which pack's files take precedence when packs overlap
- **Format-aware JSON merging** — dedicated strategies per Minecraft JSON format (models, blockstates, atlases, items, equipment, sounds, font, language, `pack.mcmeta`) so array data from multiple packs is preserved instead of silently overwritten
- **Merge provenance + `/pm inspect`** — for every output file, record which pack won and every contributor. Surface via `/pm inspect` (summary, per-pack detail, collisions, exportable report) and the plugin API
- **Validation rollback** — if a new merge trips validation errors, keep the previous pack live instead of shipping broken output to players
- **`pack_format` guardrail** — warn or error when the merged pack targets a Minecraft version different from the running server's
- **Orphan asset detection** — surface unreferenced textures and sounds so you can trim bloated merged packs
- **CustomModelData collision warnings** — logs a warning when two packs both claim the same `custom_model_data` predicate so operators get a diagnostic trail instead of a silent drop
- **In-game priority reordering** — `/pm priority up|down|top|bottom|set <pack>` edits `config.yml` and re-merges live
- **Profiles / presets** — swap whole pack compositions atomically for seasonal events or A/B tests via `/pm profile switch <name>`
- **Remote pack sources** — declare HTTPS URLs in config; PackMerger downloads and caches into `packs/.remote-cache/`, honors ETag / Last-Modified, supports bearer + basic auth with env-var substitution
- **Multiple upload providers** — self-hosted HTTP, Polymath, or any S3-compatible object store (AWS S3 / Cloudflare R2 / Backblaze B2) with content-addressed keys, retention, and optional presigned URLs
- **Bedrock / Geyser conversion** (opt-in, experimental) — converts the merged pack's custom item icons into a Bedrock pack + Geyser custom-item mappings so Bedrock players see the same custom items, with optional auto-deploy into Geyser's folders
- **Network-wide distribution** (optional) — companion proxy plugins for Velocity (`packmerger-velocity`) and BungeeCord (`packmerger-bungee`) offer the merged pack from the proxy, one pack for the network or each backend's own; backends push updates over an HMAC-signed plugin channel, the proxy remembers the last pack across restarts and swaps it in place for online players
- **Hot reload** — watches the packs folder, including files inside unzipped pack folders, and auto-merges with configurable debounce
- **Reliable delivery** — the pack is sent on every join under one stable per-server pack UUID (it replaces only PackMerger's own pack, never a proxy's or another plugin's); players who join before the first merge get the pack as soon as it is published; failed downloads are re-sent automatically (bounded); the previous pack is served immediately on startup and through `/pm reload`; identical content always produces the same SHA-1; the pack is required and enforced by default (decline or repeated download failure → kick; can be turned off); Bedrock (Floodgate) players are skipped
- **Per-server packs** — supports multi-server networks where each backend needs a different pack composition
- **Pack validation** — checks JSON syntax, pack.mcmeta structure, and missing texture/model references after every merge
- **Custom overrides** — drop a `pack.mcmeta` or `pack.png` in the packs folder to override the merged pack's metadata and icon
- **Concurrent download limiting** — built-in rate limiter for the self-host HTTP server
- **Plugin API + Bukkit events** — other plugins add their own pack with `PackMergerApi.registerPack` (removed automatically when they disable), contribute lazily from `PackMergerCollectPacksEvent`, and react to `PackMergedEvent`, `PackUploadedEvent`, `PackValidationFailedEvent`, etc. without log-scraping
- **Copy the merged pack elsewhere** — `merge.output-copy-to` drops a copy of every merged zip into folders you choose
- **`/pm verbose on|off`** — toggle debug logging at runtime; the choice is saved to `config.yml`
- **Brigadier commands** — full tab completion via Paper's command API
- **Lean jar + runtime dep loader** — the shipped jar is ~360 KB; MinIO and its S3-SDK transitive closure are downloaded from Maven Central on first enable into `plugins/PackMerger/libraries/` and verified against SHA-256. Cached across restarts.
- **Update check** — asks GitHub for this fork's latest release (pre-releases and `dev-*` builds are ignored) on enable and surfaces new releases in the console and to admins on join. Advisory only; the plugin never auto-downloads.

## Requirements

- **Paper 26.1+** (compiled against the 26.1.2 API so one jar runs on 26.1, 26.2 and 26.3; tested on 26.3) or **Folia** 26.1+
- **Java 25** or newer
- `folia-supported: true` in plugin.yml — every scheduler call routes through Paper/Folia's region-aware APIs so the plugin runs without `UnsupportedOperationException`s on Folia

## Installation

1. Build the plugin (see [Building](#building)) or download the release jar
2. Place `packmerger-plugin-1.4.0.jar` into your server's `plugins/` folder
3. Start the server — the plugin generates `config.yml` and creates the `packs/`, `output/`, and `cache/` directories under `plugins/PackMerger/`
4. Place your resource pack `.zip` files or unzipped pack folders into `plugins/PackMerger/packs/`
5. Edit `plugins/PackMerger/config.yml` to configure priority order, upload provider, and distribution settings
6. Run `/packmerger reload` or restart the server

### End-to-end tests

`./gradlew :packmerger-plugin:plugwrightTest` boots a throwaway Paper 26.3 server (latest build; port 25567) with the
built jar and fixture packs from `packmerger-plugin/src/test/e2e/fixtures/`, then drives it with
[plugwright](https://github.com/Drownek/plugwright) bots. Specs live in `packmerger-plugin/src/test/e2e/tests/`;
needs Node 22+, and reports land in `packmerger-plugin/build/reports/plugwright/`. Two test-only plugins built from
`packmerger-plugin/src/e2ePlugin/` are staged next to it: `PmApiTest` uses the public API from its own
classloader, and an empty stand-in named `ItemsAdder` lets the other-pack-host check run. Neither is shipped.

The published plugwright 3.0.0 bots stop at Minecraft 26.1, so the suite runs on the
[pcxgg fork of plugwright](https://github.com/pcxgg/plugwright) (branch `pcx/26.3`,
version `3.1.0-pcx.1`), whose runner uses the pcxgg forks of mineflayer, minecraft-protocol
and minecraft-data with 26.3 (protocol 777) support. Neither half is published yet, so check the
fork out next to this repository (`../plugwright`) and build it once:

```bash
cd ../plugwright
scripts/with-local-forks.sh npm run install:packages && npm run build:packages   # runner (see its README)
(cd gradle-plugin && ./gradlew publishToMavenLocal)                              # Gradle plugin -> ~/.m2
```

`settings.gradle` resolves the Gradle plugin from `mavenLocal()` first, and
`packmerger-plugin/src/test/e2e/package.json` links the runner by path
(`file:../../../../../plugwright/runner-package`). After changing the runner, delete
`packmerger-plugin/src/test/e2e/node_modules` so the next run reinstalls it.

Ports are overridable so several checkouts can run the suite at once:
`-Pe2ePort=25580 -Pe2eRconPort=25590 -Pe2eHttpPort=25581` (or the matching `ORG_GRADLE_PROJECT_e2e*`
environment variables). The fixture packs declare `min_format` 84 / `max_format` 97, so the
same suite also runs on 26.1.2 by changing `minecraftVersion` in `packmerger-plugin/build.gradle`.

CI (`.github/workflows/ci.yml`) runs `./gradlew build` only, which does not touch the e2e suite.
Even so, every Gradle invocation resolves the plugwright Gradle plugin, so each job first runs
`.github/actions/bootstrap-forks`: it clones `pcxgg/plugwright` at a pinned commit, publishes the
Gradle plugin to Maven local (JDK 17 toolchain) and caches the result per commit. Bump the
`plugwright-ref` default in that action after changing the fork. To run the e2e suite in CI, a job
would additionally have to build the fork's runner next to the checkout as above.

## Releasing

1. Bump `version` in `build.gradle`, turn the `[Unreleased]` section of `CHANGELOG.md` into `[x.y.z] - YYYY-MM-DD`, update `versions.json` (only read by a custom `update-check.url`; the default update check reads the GitHub releases) and refresh `spigot-resource.bbcode`.
2. Commit, tag `vx.y.z` and push the tag. The Release workflow builds the plugin, Velocity and Bungee jars and creates the GitHub release from that changelog section.
3. Upload `packmerger-plugin-x.y.z.jar` to SpigotMC and paste `spigot-update-x.y.z.bbcode` as the update post.

`spigot-resource.bbcode` is the SpigotMC resource page. SpigotMC runs XenForo 1.4, whose BBCode is limited: only `[B] [I] [U] [S] [COLOR] [SIZE] [FONT] [URL] [IMG] [LIST] [LIST=1] [*] [CODE] [QUOTE] [SPOILER] [CENTER] [LEFT] [RIGHT] [INDENT]` render. There are no tables, headings, `[ICODE]`, `[HR]` or Markdown, so section headings are centred coloured text, inline code is `[FONT=Courier New]`, and `[CODE]` blocks go inside `[SPOILER]`s rather than lists.

## Configuration

The plugin generates a fully commented `config.yml` on first run. Below is a walkthrough of each section.

### Server Name

```yaml
server-name: ""
```

Identifies this server for per-server pack configs. If empty, auto-detects from `server.properties`. Only relevant for multi-server networks.

### Priority

```yaml
priority:
  - "main-pack.zip"
  - "ui-overhaul.zip"
  - "custom-models.zip"
```

Controls merge order. The first entry has the **highest priority** — its files win when two packs contain the same non-mergeable file (e.g. textures). Packs found on disk but not listed here are automatically merged at the lowest priority, sorted alphabetically by filename. Use numeric prefixes (e.g. `01_pack.zip`, `02_pack.zip`) to control their order without needing to list them in the config.

### Per-Server Packs

```yaml
server-packs:
  lobby:
    additional:
      - "lobby-textures.zip"
    exclude: []
  survival:
    additional:
      - "survival-textures.zip"
    exclude:
      - "ui-pack.zip"
```

Allows each server to include extra packs or exclude packs from the global list. Matched by the `server-name` value (case-insensitive).

### Merge Settings

```yaml
merge:
  auto-merge-on-startup: true    # Merge automatically when the plugin enables
  model-policy: whole-file       # whole-file (default) or deep; see "Priority Order & Conflict Resolution"
  optimization:
    strip-junk-files: true       # Remove .DS_Store, Thumbs.db, __MACOSX, .git, etc.
    compression-level: 6         # ZIP compression (0-9, default 6)
    size-warning-mb: 100         # Warn if output exceeds this size (0 = disabled)
  hot-reload:
    enabled: true                # Watch packs/ (and the folders inside it) for changes
    debounce-seconds: 5          # Wait this long after last change before merging
  output-copy-to: []             # Folders (relative to plugins/, or absolute) that get a copy of every merged zip
```

`output-copy-to` is for serving the pack with something else (a web server folder, another plugin): after each merge the zip is written to a temp file in every listed folder and moved into place. A folder inside `packs/` is refused, since it would be merged again.

### Upload Provider

```yaml
upload:
  auto-upload: true              # Upload after every merge
  provider: "self-host"          # "self-host", "s3" or "polymath"
  fallback: []                   # e.g. ["s3"]: used when the provider above can't be used
```

`upload.fallback` lists providers to publish through, in order, when `upload.provider` fails to upload, or (self-host) when its reachability check fails or its auto-detected host is not routable. Only configured providers are tried. The route in use, and the reason for any fallback, is shown in `/pm status`, logged, and sent to online admins.

#### Self-Host (Default)

```yaml
upload:
  provider: "self-host"
  self-host:
    port: -1                 # -1 = Minecraft port + 1; or a port your panel allocated
    public-url: ""           # Complete URL, used as-is (only a bare http://host:port gets /pack)
    public-host: ""          # Host name or public IP for the auto-built URL
    detect-public-ip: false  # Opt-in: asks checkip.amazonaws.com / api.ipify.org for the public IP
    verify: true             # Download-check the URL after every upload
    rate-limit: 50           # Max concurrent downloads (0 = unlimited)
```

The self-host provider starts a built-in HTTP server on all interfaces and serves the pack at `/pack`. Make sure the port is open in your firewall (on Pterodactyl/Pelican-style panels, add a port allocation for it).

**The URL players are sent.** With neither `public-url` nor `public-host` set and no proxy in front (no `settings.bungeecord` in `spigot.yml`, no `proxies.velocity.enabled` or `proxies.proxy-protocol` in `config/paper-global.yml`, no `distribution.proxy-notify`), each player gets `http://<address they joined with>:<port>/pack`: the host they typed in the server list (`Player#getVirtualHost()`: LAN IP, public IP or domain; IPv6 in brackets). The pack, its SHA-1 and its pack UUID are the same for everyone, so the client cache works as before. A client that sends no usable address gets the fixed URL below, and a URL pointing at `localhost`/`127.x`/`::1` is never sent to a player who is not on the server machine (they get no pack and are not kicked; admins are told what to set). `public-url`, if set, is used exactly as written, so a reverse proxy or CDN URL such as `https://cdn.example.com/rp.zip` works (the proxy forwards to `http://<server>:<port>/pack`; requests arriving with the public URL's own path are served as well). Otherwise the URL is `http://<host>:<port>/pack`, with the host taken from the first routable of `public-host`, the opt-in public IP lookup, `server-ip` in `server.properties`, and the bind address. Loopback, private (RFC 1918), link-local, CGNAT, `0.0.0.0` and IPv6 unique-local hosts can't be reached from the internet: PackMerger still uses the best one it found (LAN players can download) but warns on every merge, tells admins on join, and `/pm status` says exactly what to set.

**Verification.** After every upload, PackMerger downloads the first KiB of the pack from `127.0.0.1:<port>` and from the advertised URL and compares the bytes (the second request also catches routers without NAT hairpinning, closed ports and proxies pointing elsewhere). It runs off the main thread; the new pack is only served at `/pack` once it is published, so the check never exposes bytes that don't match the advertised SHA-1. A failure is logged, sent to online admins, shown in `/pm status`, and switches to `upload.fallback` when one is configured. For a `public-url` you set yourself, a failing advertised-URL check only warns (some NATs and CDNs can't be reached from inside). Set `verify: false` to skip it.

**HTTP behaviour.** Exact path matching (`/packfoo` is a 404), `GET` and `HEAD`, a strong `ETag` (the SHA-1) with `If-None-Match` → `304`, single `Range` requests → `206`, `Cache-Control: no-cache` so CDNs revalidate, and the concurrent download limit (`429` when full). A download in progress keeps reading the file it started with, even if a new pack is published meanwhile.

#### Polymath (Self-Hosted)

[Polymath](https://github.com/oraxen/polymath) is a lightweight Python web server originally created by the Oraxen/Nexo project for hosting Minecraft resource packs. You must self-host your own Polymath instance — the public Oraxen instance (`atlas.oraxen.com`) has been shut down.

```yaml
upload:
  provider: "polymath"
  polymath:
    server: "https://your-polymath-host:5000"
    secret: "your-custom-secret"
    id: "my-server"
```

To self-host Polymath, you need Python installed. See the [Polymath GitHub repo](https://github.com/oraxen/polymath) for setup instructions.

### Distribution

```yaml
distribution:
  enabled: true                    # Send pack to players on join
  required: true                   # Client "required" flag (no "proceed without" button); kicks nobody by itself
  enforce-required:
    enabled: true                  # With required: true, kick players who decline / can't download after retries
    kick-message: "<red>This server requires its resource pack.</red> <gray>Rejoin and accept it to play.</gray>"
  prompt-message: ""               # Custom MiniMessage prompt (empty = Minecraft default)
  use-add-resource-pack: false     # false = remove PackMerger's previous pack, then send; true = send only (same UUID replaces in place)
  join-delay-ticks: 20             # Delay before sending (20 ticks = 1 second)
  retry:
    max-attempts: 3                # Re-sends per session after FAILED_DOWNLOAD / DISCARDED (0 = off)
    delay-ticks: 40                # Delay before each re-send
  skip-bedrock-players: true       # Don't send the Java pack to Floodgate (Bedrock) players
  on-new-pack:
    action: "notify"               # "none", "notify", or "resend"
    notify-message: "<yellow>[PackMerger]</yellow> <gray>A new resource pack is available. Rejoin or use F3+T to reload.</gray>"
  proxy-notify: false              # Push each new pack to the PackMerger proxy plugin (see Proxy below)
  proxy-secret: ""                 # Shared secret signing proxy messages; ${ENV_VAR} supported
```

### Logging

```yaml
log-level: "info"                  # "debug", "info", "warning" or "error"
```

`"debug"` logs every file merge, pack send, resource-pack status, validation check and file watcher event, for troubleshooting. `/pm verbose on` switches to `"debug"` and `/pm verbose off` back to `"info"` without a reload; the choice is saved to `log-level` in `config.yml`.

## Commands & Permissions

All commands require `packmerger.admin` permission (default: op).

| Command | Description |
|---|---|
| `/pm reload` | Reload config, re-init upload provider, re-fetch on-reload remote packs, and trigger a merge |
| `/pm merge` | Re-stage plugin packs, merge and upload, without reloading the config |
| `/pm validate` | Run validation on the current merged pack (JSON, missing textures/models, orphan assets, pack_format drift) |
| `/pm status` | Server name, provider, last merge, pack URL, hosting route and verification, last upload result, SHA-1, size, packs, each detected plugin integration and its state, API-registered packs, other plugins hosting their own pack, Bedrock/Floodgate state, log level |
| `/pm verbose [on\|off]` | Show, or switch, debug logging at runtime (saved as `log-level`) |
| `/pm fixup` | List settings of ItemsAdder/Oraxen/Nexo that conflict with PackMerger |
| `/pm fixup itemsadder\|oraxen\|nexo` | Back up that plugin's config, write the fix, and tell you which reload command to run |
| `/pm fixup dismiss` | Stop warning about the current findings (saved in `dismissed-warnings.yml`) |
| `/pm apply [player]` | Force-send the current pack to all online players, or just one (supports `@a` selectors) |
| `/pm inspect` | Summary of the last merge: pack order, per-pack file counts, collision count |
| `/pm inspect <pack>` | What this pack won + files it contributed to but lost on |
| `/pm inspect collisions` | List every output path touched by 2+ packs |
| `/pm inspect export` | Write the full merge report to `output/last-merge-report.txt` |
| `/pm priority list` | Show current priority order with 1-based indices |
| `/pm priority up\|down\|top\|bottom <pack>` | Move a pack one step / all the way in priority |
| `/pm priority set <pack> <n>` | Place a pack at absolute 1-based position |
| `/pm profile` / `/pm profile list` | List defined profiles, mark the active one |
| `/pm profile switch <name>` | Activate a profile and trigger a merge with its priority |
| `/pm fetch` | Re-download every remote pack (ignores refresh policy) |
| `/pm fetch <alias>` | Re-download one named remote pack |
| `/pm scan [refresh]` | Re-scan the datapacks and print what was found; `refresh` also repeats the Modrinth lookups. Requests a merge if something changed |
| `/pm sources [datapacks]` | Every pack source and its state (packs/, remote, plugin, API, datapacks, external); `datapacks` limits it to datapacks |
| `/pm sources pending` | External resource packs waiting for approval |
| `/pm sources info <id>` | URL, size, hashes and reason of one external pack |
| `/pm sources approve <id\|all>` | Approve, download (verified) and merge an external pack (needs `packmerger.sources.approve`) |
| `/pm sources reject <id>` | Never ask for this exact file again (needs `packmerger.sources.approve`) |
| `/pm conflicts [pack]` | Files where packs really disagree (identical copies and cleanly merged JSON are left out); datapack packs are tagged `[dp]` |
| `/pm rebuild` | Re-scan the datapacks, then merge and upload even if nothing changed |

`/pm merge`, `/pm reload`, `/pm fetch`, `/pm rebuild` and the startup merge always
merge (so Bedrock conversion, `merge.output-copy-to` and the merge events run on every
start). Other automatic merges (file watchers, datapack rescans, API changes) are
skipped when the merge inputs are unchanged and the live pack is the result of those
inputs (`[MERGE] Inputs unchanged; keeping the live pack`), so an idle rescan never
re-uploads the pack.

## How It Works

### Merge → Upload → Distribute Pipeline

1. **Discover** — scans `plugins/PackMerger/packs/` for `.zip` files and directories containing `pack.mcmeta` or `assets/`
2. **Order** — builds a merge order based on the priority config, per-server includes/excludes, and any unlisted packs
3. **Merge** — iterates packs from lowest to highest priority, collecting files into memory:
   - **Non-JSON files** (textures, sounds, shaders, etc.) use last-write-wins — higher priority overwrites lower
   - **Model and blockstate JSON** (`assets/<ns>/models/`, `assets/<ns>/blockstates/`): the higher-priority file wins whole (`merge.model-policy: whole-file`, the default), except that item-model `overrides` concat-dedup by predicate (sorted by `custom_model_data`) and blockstate `multipart` cases concat-dedup by `when`, so CustomModelData from multiple packs survives. `model-policy: deep` restores the old key-by-key deep merge
   - **Item definitions** (`assets/<ns>/items/`, 1.21.4+): two `range_dispatch` nodes on the same property have their `entries` unioned by `threshold`; two `select` nodes on the same property have their `cases` unioned by `when`; matching `fallback` nodes are merged the same way. Anything else (different node types or properties, plain `model` nodes) is not combinable: the higher-priority file wins whole and a warning names both packs
   - **Atlases, fonts, equipment**: atlas `sources` and font `providers` are concatenated; equipment files are deep merged
   - **sounds.json** (`assets/<ns>/sounds.json`) sound arrays are concatenated so sounds from all packs coexist
   - **Language files** (`assets/<ns>/lang/*.json`) key-union so translations from multiple packs compose; higher priority wins on the same key
   - **pack.mcmeta** preserves both `overlays.entries[]` and `filter.block[]` from every pack — deduped by `directory` and by `namespace|path` respectively. When a pack declares a format range, the merged pack declares the union of both ranges (`min_format`/`max_format`, plus `supported_formats` and an in-range `pack_format` for clients up to format 64), and overlay entries gain a `formats` range when the combined overlay list needs one to load
   - **Overlay directories** (`<overlay>/assets/...`) get exactly the same per-format rules as `assets/...`
4. **Override** — if `pack.mcmeta` or `pack.png` exists directly in the packs folder (not inside a pack), it replaces whatever the merge produced
5. **Validate** — the merged zip is checked for pack.mcmeta structure, JSON syntax errors, and missing texture/model references
6. **Upload & publish** — the merged zip is sent to the configured provider (self-host, S3 or Polymath). Only once that succeeds does the new `(URL, SHA-1, pack UUID)` go live, as one unit; if the upload fails, players keep getting the previous pack and `PackUploadFailedEvent` fires
7. **Distribute** — players who joined before any pack existed are sent it now; if the pack's SHA-1 changed, online players are handled according to the `on-new-pack` action. The zip is written deterministically (sorted entries, fixed timestamps), so a re-merge of identical content has the same SHA-1 and is not a "new pack"

### Priority Order & Conflict Resolution

Packs are listed highest-priority first in the config. When two packs contain the same file path:

- **Non-JSON files**: the higher-priority pack's version is used
- **Models and blockstates**: with the default `merge.model-policy: whole-file`, the higher-priority file is used as-is apart from the list concatenation below. This avoids hybrids such as an `item/generated` model inheriting another pack's 3D `elements`, or a blockstate with both `variants` and `multipart`. Set `model-policy: deep` to get the previous behaviour (keys deep-merged recursively, higher priority wins per key)
- **Item definitions** (`items/*.json`, 1.21.4+): merged only when both files dispatch the same way: `range_dispatch` entries are unioned by threshold and sorted (higher priority wins a shared threshold), `select` cases are unioned by `when` value (higher priority keeps a shared value). Otherwise the higher-priority file wins whole and a collision warning names both packs. A merged node never has both `cases` and `entries`
- **Equipment, atlases, font**: equipment is deep-merged; atlas `sources` and font `providers` are concatenated
- **Array-valued JSON fields** (`overrides`, `sources`, `providers`, `multipart` (when both files use it), `overlays.entries`, `filter.block`): concatenated across packs and deduped by a format-specific identity key (e.g. predicate, namespace/path, directory) so additions from every pack survive; higher priority wins on identity collision
- **sounds.json**: sound arrays for the same event are concatenated (higher-priority sounds listed first)
- **Language files** (`lang/*.json`): flat key-union — translations from all packs coexist, high priority wins on the same translation key
- **CustomModelData collisions**: when two packs claim the same `custom_model_data` predicate (legacy `overrides`) or the same `range_dispatch` threshold / `select` value (item definitions), the lower-priority entry is dropped and a warning is logged with the file path, the offending value and both pack names, so operators can spot "my knife turned into a pistol"-style conflicts at merge time
- **Overlays**: files under an overlay directory follow the same rules as files under `assets/`
- **Where to see it**: every collision warning and automatic rewrite is also stored with the file in the merge provenance, shown by `/pm inspect collisions` and written by `/pm inspect export`

### Plugin Pack Auto-Discovery

If you run other plugins that generate their own resource pack, PackMerger finds
each one's current pack and stages it into `packs/.plugin-packs/<alias>.zip`
before every merge, so you never have to export and copy files by hand. Staged
packs go through the **same format-aware merge** as everything else, so two
plugins that both add `custom_model_data` entries to `assets/minecraft/items/*`
or share model overrides combine instead of one silently winning; where two
files cannot be combined, the higher-priority one wins and the clash is logged.

Built-in adapters (reference the alias in `priority:` to set its precedence):

| Alias | Plugin | Source (relative to `plugins/`) |
|---|---|---|
| `oraxen` | Oraxen | `Oraxen/pack/pack.zip` |
| `nexo` | Nexo | `Nexo/pack/pack.zip` |
| `itemsadder` | ItemsAdder | `ItemsAdder/output/generated.zip` |
| `modelengine` | ModelEngine | `ModelEngine/resource pack.zip` (or the folder) |
| `elitemobs` | EliteMobs | `EliteMobs/resource_pack` (cluster) |
| `freeminecraftmodels` | FreeMinecraftModels | `FreeMinecraftModels/output/FreeMinecraftModels.zip` + `FreeMinecraftModels/resource_pack` (cluster) |
| `nova` | Nova | `Nova/resource_pack/ResourcePack.zip` |
| `betterhud` | BetterHUD | `BetterHUD/build.zip` |
| `valhallammo` | ValhallaMMO | `ValhallaMMO/resourcepack` (folder) |
| `vane` | vane-core | `vane-resource-pack.zip` (in `plugins/` or the server root) |
| `backpackplus` | BackpackPlus | `BackpackPlus/pack/resourcepack.zip` |
| `betterstructures` | BetterStructures | `BetterStructures/resource_pack` (cluster) |
| `cannonrtp` | CannonRTP | `CannonRTP/resource_pack` (cluster) |
| `eternaltd` | EternalTD | `EternalTD/resource_pack` (cluster) |
| `infinitevehicles` | InfiniteVehicles | `InfiniteVehicles/InfiniteModelPack.zip` |
| `megablocksurvivors` | MegaBlockSurvivors | `MegaBlockSurvivors/resourcepack` or `/resource_pack` |
| `resurrectionchest` | ResurrectionChest | `ResurrectionChest/resource_pack` (cluster) |
| `mmoinventory` | MMOInventory | download from the author's published link (see below) |
| `realisticsurvival` | RealisticSurvival | download from the author's published link (see below) |

How staging works:

- **Clusters.** A cluster is a folder holding several packs (folders or zips).
  They are unioned into one staged pack: the alphabetically first pack wins
  plain-file clashes, and lang, atlas, sounds and model JSON is merged. A folder
  that is not a pack itself but contains packs is treated as a cluster
  automatically.
- **Validation.** A staged source must have `pack.mcmeta` or `assets/` at its
  root (a zip wrapped in a single folder is unwrapped). Anything else, including
  an unreadable zip, is skipped with a console line and listed in the advisory
  admins see on join. PackMerger also warns when ItemsAdder's zip protection or
  JSON compression is on, since those make `generated.zip` unmergeable.
- **No half-written packs.** A changed source is only copied once its size and
  modification time hold steady across `plugin-packs.stability.polls` readings
  (default 3, one second apart). A source that is still being written is retried
  once it settles; the previous staged copy stays in use meanwhile.
- **Automatic re-merge.** `plugin-packs.watch` (on by default, every 5 s) polls
  the resolved source paths and merges when a plugin rebuilds its pack, so
  `/oraxen reload`, `/iazip` and friends need no `/pm` command. `/pm merge`
  forces a merge at any time.
- **Stale cleanup.** When a plugin is removed, its adapter is disabled, or its
  source disappears, the staged copy is deleted so it stops merging. The same
  applies to `packs/.remote-cache/` when an alias is removed from `remote-packs`.

Overrides and your own adapters live under `plugin-packs.sources.<alias>`:
`enabled: false` skips a plugin, `path:` (one path or a list) points at a
non-default location, `cluster: true` reads the path as a folder of packs, and
`plugin:` names the plugin that must be installed. Any alias that is not built
in becomes a new adapter, so a plugin PackMerger does not know yet needs no
release:

```yaml
plugin-packs:
  sources:
    my-plugin:
      plugin: "MyPlugin"
      path: "MyPlugin/generated/resource_pack"
      cluster: true
```

**Network note:** MMOInventory and RealisticSurvival only publish their packs as
a download. When (and only when) one of those plugins is installed, PackMerger
downloads its pack from the author's Dropbox link on startup and on `/pm reload`
and caches it in `packs/.plugin-packs/`. Set `sources.<alias>.enabled: false` to
opt out, or `sources.<alias>.path` to use a local copy.

Because other plugins build their packs as they start up, the first merge is
delayed by `plugin-packs.merge-delay-seconds`.

### Other Plugins Hosting Their Own Pack

ItemsAdder, Oraxen and Nexo can upload and send their own pack. Next to
PackMerger that means two packs per player, and theirs can replace the merged one.
PackMerger reads their config on startup, on `/pm reload` and before every merge,
and reports what it finds on the console, in `/pm status` and to admins a few
seconds after they join:

| Plugin | File | Reported when | `/pm fixup` sets |
|---|---|---|---|
| ItemsAdder | `config.yml` | `resource-pack.hosting.self-host`, `simple_self_host`, `external-host` or `lobfile` `.enabled: true` | those to `false`, and `resource-pack.hosting.no-host.enabled: true` |
| ItemsAdder | `config.yml` | `resource-pack.zip.protect-file-from-unzip.protection_1/2/3` (or the older `.enabled`/`.extreme`) `: true` — the zip can't be read | `false` |
| ItemsAdder | `config.yml` | `resource-pack.zip.compress-json-files: true` — the JSON can't be merged reliably | `false` |
| Oraxen | `settings.yml` | `Pack.upload.enabled: true`, `Pack.dispatch.send: true` (older versions: `Pack.dispatch.send_pack`, `Pack.generation.protection`) | `false` |
| Nexo | `settings.yml` | `Pack.server.type` is set and not `NONE` | `NONE` |

Only keys that are present are checked; a missing key never produces a warning.
`/pm fixup <itemsadder|oraxen|nexo>` copies the file to
`<file>.packmerger-backup-<date>` first, keeps its comments, writes through a temp
file and refuses if the file changed meanwhile. It then tells you what to run so
the plugin picks it up (`/iareload` then `/iazip`; `/oraxen reload all`;
`/nexo reload all`, or a restart); PackMerger's watcher re-merges the regenerated
pack. `/pm fixup dismiss` hides the current warnings (stored in
`plugins/PackMerger/dismissed-warnings.yml`); a different setting shows up again.

### Remote Pack Sources

Declare packs in config that come from an HTTP(S) URL and PackMerger will
download them into `packs/.remote-cache/<alias>.zip` before merging. Reference
them in `priority:` by alias (no `.zip`). Supports ETag / Last-Modified caching,
bearer + basic auth, and `${ENV_VAR}` substitution in URL and token fields.

```yaml
remote-packs:
  quality-armory:
    url: "https://github.com/user/repo/releases/latest/download/pack.zip"
    refresh: "on-startup"     # "on-startup" | "on-reload" | "manual"
    auth:
      type: "bearer"
      token: "${GITHUB_TOKEN}"
```

Use `/pm fetch` or `/pm fetch <alias>` to force a re-download outside the
configured refresh policy. If a fetch fails but a cached copy exists,
PackMerger uses the cache and logs a warning — transient network failures
don't take your pack offline.

### Datapack Resource Packs

Many datapacks (world generation, structures, custom items) ship textures, models or
sounds that players only see with a matching resource pack. PackMerger finds those
resource packs on its own, merges them with everything else and sends the result to
players. Nothing to install besides PackMerger; the feature is on by default
(`datapacks.enabled: true`, since config-version 7). Players download only the merged
resource pack; the datapacks themselves stay on the server.

**What is scanned.** The server's datapack folder (`<level-name>/datapacks/`, e.g.
`world/datapacks/`), the `datapacks/` folder of every other loaded world (Multiverse and
similar) and any `datapacks.extra-folders`. Zips and extracted folders count; hidden
files and uploads in progress (`.part`, `.tmp`, `.crdownload`, `.filepart`, `.!ut`,
`.download`) are ignored. **Paper only loads datapacks from the level folder**
(`<level-name>/datapacks/`), so a datapack in another world's folder is not active on the
server: it is listed in `/pm sources datapacks` ("folder not loaded by the server") but,
with `only-enabled: true` (default), not merged — players would otherwise download
assets for a datapack the server does not run. When the same datapack is in both
places, the copy in the level folder keeps the plain alias (`dp-<name>`).

**What is found** in each datapack (first match wins):

| Layout | Example | Staged as |
|---|---|---|
| `assets/` next to `data/` ("hybrid" datapack) | `Terralith.zip` with `data/` and `assets/` | `dp-terralith`, with a generated `pack.mcmeta` for the running Minecraft version |
| A resource pack folder inside the datapack (a top-level folder with `assets/` and no `data/` of its own) | `resourcepack/pack.mcmeta` + `resourcepack/assets/…` | `dp-<name>`, keeping that pack's own `pack.mcmeta` and overlays |
| A resource pack zip inside the datapack (one level deep) | `Incendium RP.zip` inside `Incendium.zip` | `dp-<name>` |
| A resource pack put into `datapacks/` | a zip with `assets/` and no `data/` | `dp-<name>` |
| Declared on Modrinth (downloaded automatically, verified) | the datapack's Modrinth version lists a resource pack | `dp-<name>-rp` |
| Nothing | a normal data-only datapack | not staged — this is normal |

Only `assets/**`, `pack.png` and a resource-pack `pack.mcmeta` are copied into
`packs/.datapack-packs/<alias>.zip`; a datapack's `data/**` and its own (data-format)
`pack.mcmeta` never reach the resource pack. A kept `pack.mcmeta` loses its `filter`
section (and any other key but `pack`, `overlays`, `language`), so a datapack cannot hide
vanilla assets for every player. Staged packs merge like plugin packs: by default below
everything else, server-specific `additional` packs included (`datapacks.position: bottom`,
so your own packs win), and you can place an alias anywhere in `priority:` or with
`/pm priority`.

**When it runs.** On startup (before the first merge), on `/pm scan`, when a file in a
watched datapack folder changes (`datapacks.watch`, debounced like hot reload, with a
60-second poll for folders the OS cannot watch), when a world is loaded or unloaded,
and after `/minecraft:reload` or `/datapack enable|disable`. A merge is requested only
when something that matters changed. A datapack that is still being uploaded is not
read: its size and timestamp must stay the same for `stability.polls` readings, and a
zip that cannot be read yet is retried for a minute before it is reported as corrupt.

**Safety.** Datapacks and downloads are read with limits (`datapacks.limits`: file
size, total and per-entry uncompressed size, entry count, compression ratio), entry
names that try to leave the pack (`../`, absolute paths, drive letters), symlinks and
(in folder datapacks) NTFS junctions or other links pointing outside the pack are
skipped, and nothing from a datapack is ever executed. Because the merge holds every
file in memory, JSON is bounded too: a `.json`/`.mcmeta` file over 4 MiB is skipped
(warning in the console), all staged datapack packs together may hold 64 MiB of JSON,
and `max-uncompressed-mb` caps all of them together, not just each one. A datapack over a
limit is skipped and reported in `/pm sources datapacks`. Modrinth lookups never hold up
the startup merge or a server stop: the first merge uses cached results and files
already downloaded, and new downloads are merged as soon as they finish.

```yaml
datapacks:
  enabled: true
  only-enabled: true        # only datapacks the server has enabled (/datapack list)
  extra-folders: []
  position: bottom          # unlisted datapack packs: bottom (lowest priority) or top
  watch: true
  external:
    modrinth:
      enabled: true         # PRIVACY: sends the datapacks' SHA-1 hashes to api.modrinth.com
      allowed-hosts: ["cdn.modrinth.com"]
      auto-approve: true    # download found resource packs without asking (verified)
      trusted-projects: []  # with auto-approve: false: project IDs (not slugs) approved automatically
```

#### External resource packs from Modrinth

Some datapacks publish their resource pack separately. With
`datapacks.external.modrinth.enabled: true` (the default) PackMerger looks up each
datapack **zip** on Modrinth **by its SHA-1** — never by name — and takes only what the
author declared: a resource-pack file uploaded with the same version
(`required-resource-pack`, plus `optional-resource-pack` with `include-optional`), or a
`required` dependency on a resource-pack project (the pinned version, or else the
newest release — then beta, never alpha — for the server's Minecraft version).
Results are cached for `lookup-cache-hours` (also "not on Modrinth"). After a failed
lookup or a rate limit, automatic scans leave Modrinth alone for at least 5 minutes (or
until Modrinth's own reset time); `/pm scan refresh` asks again at once.

With the default `auto-approve: true`, a found resource pack is downloaded and merged
without asking. Every download is HTTPS only, every redirect must stay on
`allowed-hosts`, the size is capped (`max-download-mb`) and the file is verified against
Modrinth's SHA-512 (and SHA-1 and size) before it is used; it is kept in
`cache/modrinth/<sha512>.zip` and never downloaded twice.

To decide yourself, set `auto-approve: false`. Found files then wait for an admin:

```
> /pm scan
  ! mr-3f9a1c22  Modrinth dungeons-and-taverns-rp 4.4.1 for dnt-v4.zip — waiting for approval
> /pm sources pending
> /pm sources info mr-3f9a1c22
> /pm sources approve mr-3f9a1c22      (or: /pm sources reject mr-3f9a1c22)
```

An approval is bound to the exact file (its SHA-512); a new version of the pack asks
again, unless its project ID is in `trusted-projects`. Only project **IDs** count (8
letters/digits, shown on the project page, compared exactly): slugs can be renamed and
then taken by someone else, so a slug in the list is ignored with a warning. Decisions
are stored in `plugins/PackMerger/external-sources.json`; an unreadable entry there is
skipped on its own instead of discarding every decision. Approving and rejecting is
only accepted from a player (with `packmerger.sources.approve`) or the server console /
RCON — not from command blocks, other entities or `/execute as` (so a datapack function
cannot approve its own downloads through an entity). Paper cannot tell a datapack
function that runs as the server apart from the console; that case is not blocked, but
it only matters with `auto-approve: false` (by default everything is approved anyway,
still verified as above). Admins see "N external resource pack(s) wait for approval"
when they join.

#### Limitations — when a datapack's resource pack cannot be found

- **Resource pack only linked in a description or on another site.** PackMerger
  matches nothing by name. Download that pack yourself and drop it into `packs/`.
- **Datapack not from Modrinth, or modified.** The hash lookup only matches the exact,
  unmodified file uploaded to Modrinth. Extracted (folder) datapacks, re-zipped packs and
  packs from CurseForge, PlanetMinecraft or GitHub show up as "not on Modrinth".
- **Dependency with only a file name**, or a resource-pack project without a release or
  beta for your Minecraft version: logged as `[unsupported]` / `[missing-dependency]`,
  nothing is guessed. If Modrinth spells the game version differently from the server
  (e.g. `26.2` vs `26.2.1`), PackMerger also tries `major.minor`.
- **Datapacks added by plugins** (Paper's lifecycle API) live inside plugin jars and are
  not scanned; the plugin can register its pack through `PackMergerApi` instead.
- **Nested zips deeper than one level** are ignored.
- **Hybrid datapacks with resource-pack overlays in their root `pack.mcmeta`** lose those
  overlays (the data-format `pack.mcmeta` is replaced, and its overlay formats are
  datapack formats, not resource-pack formats); rare.
- **Folders the server does not load** (e.g. `datapacks/` inside a Multiverse world):
  Paper only loads `<level-name>/datapacks/`, so these datapacks are not active and are
  only merged with `datapacks.only-enabled: false`.
- **Oversized JSON** (a single `.json`/`.mcmeta` over 4 MiB, or more than 64 MiB of JSON
  across all datapack packs) is skipped with a warning; such packs are almost always
  broken or malicious.
- **`filter` in a datapack resource pack's `pack.mcmeta`** is removed; a pack that relies
  on hiding vanilla assets has to be put into `packs/` by hand.

The merged pack is required and enforced by default (`distribution.required: true`,
`distribution.enforce-required.enabled: true`): players who decline (or whose download
keeps failing after the retries) are kicked with `enforce-required.kick-message`. When
downloads fail for good for 3 different players with no successful load in between,
failed downloads stop kicking (one warning for admins) until the next successful load;
declining always kicks.

### Profiles / Presets

Flip between whole pack compositions atomically — useful for seasonal events
or A/B testing. When `active-profile` is set, its `priority` and
`server-packs` sections shadow the root-level keys. Absent = backwards-
compatible with pre-1.1.0 configs.

```yaml
active-profile: "default"
profiles:
  default:
    priority:
      - "main-pack.zip"
  halloween:
    priority:
      - "halloween-overlay.zip"
      - "main-pack.zip"
```

Switch with `/pm profile switch halloween` — PackMerger updates `active-profile`
in config, reloads, and re-merges immediately.

### S3-Compatible Upload

Set `upload.provider: "s3"` to push merged packs to any S3-compatible object
store — AWS S3, Cloudflare R2, or Backblaze B2. One config works for all three;
only the endpoint changes.

```yaml
upload:
  provider: "s3"
  s3:
    endpoint: "https://<account>.r2.cloudflarestorage.com"
    region: "auto"           # R2 accepts "auto"; AWS wants the canonical name
    bucket: "my-packs"
    access-key: "${S3_ACCESS_KEY}"
    secret-key: "${S3_SECRET_KEY}"
    public-url-base: "https://packs.example.com"    # CDN in front of the bucket
    key-strategy: "content-addressed"                # <sha1>.zip, clients cache cleanly
    retention:
      keep-latest: 5                                  # old keys pruned after each upload
```

Private buckets: set `acl: "private"` and the provider returns a short-lived
presigned URL instead. The JAR ships MinIO's SDK shaded and relocated, so it
coexists with other plugins that bundle OkHttp or Jackson.

### Bedrock / Geyser Conversion (experimental)

If you run [Geyser](https://geysermc.org/), set `bedrock.enabled: true` and
PackMerger will convert the merged pack's custom items into a Bedrock resource
pack plus a Geyser custom-item mappings file, so Bedrock (Floodgate) players see
the same custom items as Java players. The `.mcpack` and `<name>.geyser.json` are
written to `output/bedrock/` and, with `auto-deploy-to-geyser: true`, copied into
Geyser's `packs/` and `custom_mappings/` folders (restart/reload Geyser to apply).
Geyser's folder is found automatically (the data folder of an installed `Geyser-*`
plugin, else `plugins/Geyser-Spigot` or `plugins/Geyser-Paper`); set
`bedrock.geyser-folder` to override it. The `.mcpack` manifest version is derived
from the converted content, so Bedrock clients download the pack again when the
items change instead of keeping a cached copy. `/pm status` shows the last
conversion, the Geyser folder and whether Floodgate is installed.

**Scope:** this converts 2D custom item icons declared via the 1.21.4+
item-definition format (`custom_model_data` → model → `layer0` texture). 3D
block/geometry models are not yet converted and are reported as warnings (enable
`bedrock.debug` to list them). It's off by default — turn it on only if you run
Geyser, and verify the result with a real Bedrock client.

### Proxy (Velocity / BungeeCord)

For proxy networks, PackMerger ships two proxy plugins built from the same core:
**`packmerger-velocity`** (Velocity 3.4+, Java 21+) and **`packmerger-bungee`** (BungeeCord
and forks, Java 17+). They decide which pack each player should have and offer it once
per session, under one stable pack id, so an update or a server switch replaces the pack
in place instead of stacking a second copy. They reuse whatever hosting your backends
already use: the proxy only needs the URL and SHA-1.

**Getting the pack to the proxy.** Either set `url=` (and `sha1=`) in the proxy plugin's
`config.properties`, or set `distribution.proxy-notify: true` on the backend(s) that
merge the pack. After every new upload the backend pushes the URL + SHA-1 to the proxy
over the `packmerger:pack` plugin channel. Plugin messages need a connected player, so
when nobody is online the push waits and goes out through the next player who joins
(`/pm status` shows `Proxy link: ... update pending until a player joins`). The proxy
stores what it was sent in `state.properties`, so a proxy restart keeps offering the
last pushed pack; editing `url=` in `config.properties` takes over again on the next
proxy start. With `resend-on-update=true` (default) players already online are offered
the updated pack straight away.

**Authentication.** Set the same long random secret as `secret=` in the proxy's
`config.properties` and as `distribution.proxy-secret` in every backend's `config.yml`
(`${NAME}` reads an environment variable on both sides). Messages are then signed with
HMAC-SHA256 and the proxy rejects unsigned, forged and replayed (older) updates, so a
backend without the secret can't replace the network pack. Without a secret the proxy
accepts any backend's update and logs a warning on startup.

**One pack or one per server.** `mode=network` (default) offers one pack everywhere: the
latest one a backend published. If several backends run PackMerger with
`proxy-notify`, list the one that owns the network pack in `accept-from=` (the proxy
warns when two backends publish competing packs). `mode=per-server` offers each
backend's own pack when a player connects to it (backends that never published one get
`url=`).

**Avoid the double send.** When the proxy distributes the pack, set
`distribution.enabled: false` on the backends. Otherwise players get it twice, once from
the backend (under the backend's pack id) and once from the proxy; PackMerger warns about
this on startup.

**BungeeCord specifics.** BungeeCord has no API to send resource packs, so the Bungee
plugin can't send the pack itself. It asks PackMerger on the backend the player is on to
send it, with a signed request (about a second after the player reaches the backend).
That means:

- `secret=` / `distribution.proxy-secret` is required; backends refuse unsigned requests.
- PackMerger must be installed on the backends players connect to (with
  `distribution.enabled: false` there). The proxy asks once per pack and session: a
  player whose backend has no PackMerger gets the pack only after the next update or
  login on a backend that has it.
- `ip_forward: true` (UUID forwarding) must be set in BungeeCord's `config.yml` and the
  backends must accept it (`bungeecord: true` in `spigot.yml`/Paper's proxy settings), so
  the backend sees the proxy's player UUID. Offers are for one player's UUID; without
  forwarding the UUIDs differ and the backend rejects them with "the offer is for another
  player".

`config.properties` (created with comments on first start; keys added in a later version
are appended to an existing file):

```properties
url=
sha1=
required=false
prompt=
secret=${PACKMERGER_SECRET}
mode=network
accept-from=
resend-on-update=true
```

The data folder is `plugins/packmerger/` on Velocity and `plugins/PackMerger/` on BungeeCord.

> Three jars are published with each release: `packmerger-plugin-<version>.jar` (backend),
> `packmerger-velocity-<version>.jar` and `packmerger-bungee-<version>.jar` (proxies).
> Update the proxy and the backends together: the 1.2 proxy plugin ignores messages from
> newer backends (it logs them as malformed), and newer proxies only accept the old unsigned
> format when no secret is set.

### Plugin API

Other plugins can add their own resource pack to the merge, query the merged pack
and react to PackMerger's events. Add `depend: [PackMerger]` (or `softdepend`) to
your `plugin.yml` and compile against the PackMerger jar (`compileOnly`). See
`docs/api-example.java` for a complete example.

```java
PackMergerApi api = PackMergerApi.get();   // or Bukkit.getServicesManager().load(PackMergerApi.class)

// Add a pack (folder or zip). Staged into packs/.api-packs/<alias>.zip before every
// merge; removed automatically when your plugin is disabled.
api.registerPack(this, "myplugin", getDataFolder().toPath().resolve("resource_pack"));
api.registerPack(this, "myplugin-extra", URI.create("https://cdn.example.com/extra.zip"));
api.unregisterPack("myplugin-extra");

String url = api.getCurrentPackUrl();
MergeProvenance prov = api.getLastMergeProvenance();
api.triggerMerge();
```

- A registered pack goes through the same checks as discovered plugin packs: it must
  have `pack.mcmeta` or `assets/` at its root, a folder of several packs is unioned
  (`PackOptions.defaults().withCluster(true)`), and a pack that is still being
  written is only copied once it is stable. Download URLs must be `https` unless
  `withAllowHttp(true)` is set; they are fetched on registration, startup and
  `/pm reload`, with ETag/Last-Modified.
- Operators place it with the alias in `priority:` like any other pack; unlisted, it
  merges below the listed packs. `/pm status` lists API packs and their owners.
- Registering schedules a merge (registrations made while plugins enable are picked
  up by the startup merge; bursts are coalesced). `withMergeNow(false)` skips it.
- To contribute only when a merge actually runs, listen to
  `PackMergerCollectPacksEvent` (fired asynchronously at the start of every merge)
  and call `event.registerPack(...)`; it is included in that merge.

Events (in `sh.pcx.packmerger.api.events`; asynchronous except
`PackSentToPlayerEvent`, which fires on the player's region thread):
`PackMergerCollectPacksEvent`, `PackMergeStartedEvent`, `PackMergedEvent`,
`PackUploadedEvent`, `PackUploadFailedEvent`, `PackValidationFailedEvent`,
`PackSentToPlayerEvent`, `PackBedrockConvertedEvent`.

> Before this release the API and events could not be used from other plugins:
> PackMerger loads its code in an isolated classloader, so other plugins saw
> different `PackMergerApi` and event classes (the cast in the old example failed,
> and listeners never fired). The API package is now shared with other plugins.

### Per-Server Pack Output

On a multi-server network, each backend server can have its own merged pack by defining `server-packs` entries in the config. Each server's `additional` packs are merged at lowest priority (below the global list), and `exclude` packs are skipped entirely. The output file is named `<server-name>-merged-pack.zip` to avoid conflicts.

### Hot Reload

When enabled, a background thread watches the `packs/` folder for file system events (create, modify, delete). To avoid excessive re-merges during bulk operations, events are **debounced** — the merge only triggers after no new events have arrived for the configured debounce period (default: 5 seconds).

### Delivery

- **Every join gets the pack.** The Minecraft client drops server packs when it disconnects, so PackMerger sends the pack on every join. The client caches downloads by SHA-1, so an unchanged pack is applied from its cache without downloading again.
- **Stable pack identity.** The pack UUID is `UUID.nameUUIDFromBytes("packmerger:" + server-name)`: the same across merges and restarts, different per backend. Sending a new pack replaces PackMerger's own pack in place; packs sent by a proxy or other plugins are never removed.
- **Early joiners.** A player who joins before the first pack is published is remembered and sent the pack the moment it is published (regardless of `on-new-pack.action`).
- **Available from the first second.** On startup, and after `/pm reload`, the merged pack already in `output/` is published again right away, before the (delayed) merge. The self-host HTTP server keeps running through `/pm reload` when its port is unchanged, and it serves a snapshot (`output/.self-host/<sha1>.zip`), so a merge in progress never changes the bytes behind the advertised SHA-1.
- **Self-heal.** If a client reports `FAILED_DOWNLOAD` or `DISCARDED` for PackMerger's pack, it is sent again after `retry.delay-ticks`, at most `retry.max-attempts` times per session. `INVALID_URL` and `FAILED_RELOAD` are not retried; the console explains what to check instead. Status reports for other plugins' packs are ignored.
- **Required packs.** `required: true` sets the client flag. With `enforce-required.enabled: true`, PackMerger also kicks players who decline, or whose download still fails after the retries. Both are on by default since 1.4.0 (configs from older versions keep their values; PackMerger logs a startup hint when the pack is not forced).
- **Bedrock players.** With Floodgate installed, Bedrock players are not sent the Java pack (`skip-bedrock-players`).

## Troubleshooting

### Merged pack not sending to players

- Check that `distribution.enabled` is `true` in config
- Verify a pack is published: run `/pm status` and check that Pack URL is not "N/A"
- Check the console for upload errors — if the very first upload failed, no URL is available to send (players who joined meanwhile get the pack as soon as one is published)
- Look for `giving up`, `INVALID_URL` or `FAILED_RELOAD` warnings: they name the player and what to check
- Bedrock (Floodgate) players are skipped on purpose (`distribution.skip-bedrock-players`)
- Ensure `upload.auto-upload` is `true`

### Self-host port already in use

- Another process is using the configured port (`-1` = Minecraft port + 1, e.g. 25566)
- Change `upload.self-host.port` to an unused port; PackMerger warns when it equals the Minecraft port, `rcon.port` or `query.port`
- Check with `netstat -tlnp | grep <port>` (Linux) or `netstat -an | findstr <port>` (Windows) to find the conflicting process
- While the port can't be bound, uploads fail (players keep the previous pack) and `upload.fallback` is used if configured

### Players can't download the self-hosted pack

- Run `/pm status`: it shows the hosting route, the resolved host and where it came from, and the last verification result with its reason
- `URL mode: per player`: players download from the address they joined with on the self-host port. If downloads fail, that TCP port is blocked by the server machine's firewall or not forwarded on the router (or players join through a proxy/tunnel/SRV record: set `public-url`)
- `Not reachable from the internet`: set `upload.self-host.public-url` (full URL) or `public-host` (your domain or public IP), or enable `detect-public-ip`
- `Verification: FAILED (advertised URL check failed ...)`: the port isn't forwarded/open, your router doesn't support NAT hairpinning, or a reverse proxy points elsewhere. Fix the network, or configure `upload.fallback: ["s3"]` with an S3/R2 bucket

### Pack validation warnings

- **"Invalid JSON"** — a JSON file has syntax errors. Open it in a JSON validator to find the issue
- **"Missing texture"** — a model references a texture path that doesn't exist in the merged pack. The texture may be in a pack that was excluded or not added
- **"Missing model"** — a blockstate references a model that doesn't exist. Same cause as missing textures
- Validation warnings don't prevent the pack from being sent — they indicate potential visual issues in-game

### Players still see the old pack after a merge — was there a rollback?

Since 1.1.0, PackMerger writes new merges to `<output>.new.zip` first and
only promotes to the real output file if validation passes. If the new merge
produces validation errors and `validation.rollback-on-errors: true` (the
default), the previous pack stays live and `PackValidationFailedEvent` fires
with `rolledBack=true`.

- Check the console for `[VALIDATION]` + `rolled back` entries
- Fix the validation errors in the offending pack and `/pm reload`
- To ship despite errors (not recommended), set `validation.rollback-on-errors: false`
- First-run case: if no previous pack exists yet, the broken pack ships anyway
  with a loud error so the initial merge isn't a permanent stall

### Orphan asset warnings are too noisy for my pack set

Orphan detection (1.1.0+) scans the merged output for textures/sounds that no
JSON references. It can false-positive on packs that use regex (`filter`) atlas
sources, which PackMerger doesn't expand.

- Disable per-install: `validation.detect-orphans: false`
- Reduce the listed entries: `validation.orphan-report-limit: 5`
- Run `/pm inspect export` to see the full list in
  `output/last-merge-report.txt` if you want to audit and trim manually

### `pack_format` mismatch warning on every merge

The 1.1.0 validator compares the merged pack's `pack_format` to the running
MC version. If you're stacking packs targeting a mix of versions, the output's
value is whatever the highest-priority `pack.mcmeta` says.

- Update the pack declaring the old format, or
- Add a `supported_formats` range to its `pack.mcmeta` that includes your server's expected format, or
- Set `validation.pack-format-check: "off"` to disable the check entirely

### "CustomModelData collision" warning in the console

- This warning is emitted when two packs both define an `overrides` entry with the same `predicate` (e.g. both claim `custom_model_data: 1000001` on `minecraft:iron_sword`)
- The higher-priority pack's entry wins; the lower-priority entry is dropped
- The warning lists the file path and the offending predicate so you can reassign one side's CustomModelData to a different number to avoid the conflict
- This is informational — the pack still ships successfully. The warning exists so you aren't surprised at runtime when one pack's custom model silently replaces another

### Hot reload not detecting changes

- Check that `merge.hot-reload.enabled` is `true`
- The file watcher only monitors the top-level `packs/` directory — changes inside subdirectories of an unzipped pack may not be detected
- For unzipped packs, try re-saving the pack's root directory or touching a file in the `packs/` folder
- Check the console for "File watcher key invalidated" — this means the packs directory was deleted or moved while the watcher was running

### Players download the pack again after every merge

- Since 1.3.0 merged zips are byte-identical when their content is unchanged, so the SHA-1 only changes when a pack really changed, and clients re-use their cached download otherwise
- If the SHA-1 still changes on every merge, one of your source packs changes on every build (for example a plugin that regenerates its zip with new content); compare two `/pm inspect export` reports
- The old `distribution.cache` setting is gone: it skipped sending the pack on rejoin, which left returning players with no pack at all (the client drops server packs on disconnect). Remove the section from older configs and delete `plugins/PackMerger/cache/player-cache.json`

### Proxy networks: pack sent twice, or the proxy offers an old pack

- Players get two copies: the backends still send their own pack. Set `distribution.enabled: false` on the backends when the proxy distributes it.
- The proxy offers an old pack: check the proxy log for `ignored a pack message from <server>: ...`. `bad signature` means the secrets differ; `not listed in accept-from` means that backend isn't allowed to publish. On the backend, `/pm status` shows `Proxy link: ...`; `update pending until a player joins` means nobody was online yet, and a `does not listen on packmerger:pack` warning means the proxy plugin isn't installed.
- BungeeCord: nobody gets the pack from the proxy. Set the secret on both sides (the proxy logs a severe message without one), install PackMerger on the backends, and set `ip_forward: true` in BungeeCord's `config.yml`; without UUID forwarding the backend logs `rejected a pack offer ...: the offer is for another player`.

### Pack too large / download timeouts

- Check the output file size with `/pm status`
- Increase `merge.optimization.compression-level` (up to 9) for smaller files
- Remove unnecessary packs or textures from the packs folder
- For very large packs (200+ MB), consider using a CDN or Polymath for faster downloads

## Metrics

PackMerger uses [bStats](https://bstats.org/plugin/bukkit/PackMerger/32086) to collect
anonymous usage statistics (server count, versions, etc.). No personal or
server-identifying data is collected. To opt out, set `enabled: false` in
`plugins/bStats/config.yml` (this disables bStats for every plugin on the server).
